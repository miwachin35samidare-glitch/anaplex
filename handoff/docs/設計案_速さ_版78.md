# 設計案：速さ（版78〜）— 2026-10-14

【み】10-14「結局さ、その時間の壁を超えないといけないんよね」「本当は1歩1周でやりたいところを…10msにまとめてやってるはず」
決まり：速さは意味（振る舞い）を変えない手だけ（10-10【み】）。精度を落とす・周回を減らす・粗く回す・飛ばす は入れない

## 1 今の1歩（版77）【測】measure_speed75（10-14、torch 2.14.1・ROCm 7.14）
- 1歩 27.1ms（実時間 10.67ms の 2.5倍）
- GPU が働いている時間 約20.8ms/歩 ／ カーネルの呼び出し 約2,000回/歩（CPU 約8ms）／ CPU が GPU を待つ 23回/歩
- GPU の中身：まとめた核（_sum・_flush・学び）約6ms ／ 残り約15ms は小さな計算（取り出し・掛け算・写し・比べる…）が数千回、1回 4〜15µs
⇒ **律速は GPU**。HIP グラフで CPU の分を消しても、壁の時間は GPU の 約21ms までしか縮まない【計算】

## 2 どこを縮めるか
| 手 | 縮むもの | 形を毎歩同じにする作り替え | コンテナ（CPU）で値を確かめられるか |
|---|---|---|---|
| A 周回の中の体ごとの計算を torch.compile で数個の核に | GPU 約15ms のうち大半 ＋ 呼び出しの数 | 要らない（dynamic） | できる（版76・77 と同じ確かめ） |
| B 形を毎歩同じに ＋ HIP グラフ | CPU の呼び出し・待ち | 要る（大きい） | 作り替えはできる。グラフそのものは GPU だけ |

**順番の提案：A（版78）→ B（版79）**【C】
- A が効く所（GPU 15ms）が今いちばん大きい。B だけでは 21ms で止まる
- A は形を変えずに入る。呼び出しも減るので、B で消す CPU の分も小さくなる
- 見込み【見】：A で GPU 21 → 約10ms・呼び出し 2,000 → 数百 ⇒ 1歩 約11〜13ms。B で 約10ms 前後（実時間の内側に入るかの境目）

## 3 版78（A）の中身
周回（_pass）の中で、体ごと（120万）に回している計算を、乱数を引く所・辺を集める所の間で区切り、純粋な関数にして torch.compile でまとめる
- 区切り1：届いた入力 → 見込み p → 表現の撃つか・補完（exc・ihn・x_all・cl_drive・v_carry・閾値・th_gain）
- 区切り2：的 → 誤差 → 抑制の体 → 不応期 → この歩のどこかで撃ったか（_any）
- 区切り3：恒常性（rate_ema・scaling・scale_up）・足し合わせの持ち越し（v_carry）・周回の中の発火（within）
- 乱数（自発のくじ）は今の順のまま外で引いて、区切りに渡す（くじの順を変えない）
- 版77 と同じく番号の assert を外した形。値は版77 と同じ（コンテナで check、くじは期待値に置き換えて並べる）

## 4 版79（B）の中身（版78 の測りを見てから細かく決める）
- 撃った辺を「決まった大きさの箱」に詰める：1歩の頭で数を1回だけ読み（同期 1回）、大きさを段（例 1.25倍ずつ）で選ぶ。段ごとにグラフを1つ
  - 周回の中で新しく撃った送り手の辺：周ごとに数を1回読む（同期 9回/歩。グラフの間なので1回 数十µs）
  - 詰め方は累積和（probe_gpu2 で nonzero と同じ並び・CPU を待たない 0.11ms）
- Python の数（t・kcur・_pc・k・hist_i）を GPU の箱に移す（グラフは Python の数を焼き付けてしまうため）
- 付け直し（self.x = …）を中身の書き換えに（グラフは配列の置き場所を覚えるため）
- 1歩1回のもの（脳幹・中脳・CL・17本の表）も1つのグラフに
- グラフにしないもの：刈り込み（配列を並べ替えるので、そのあとグラフを撮り直す）・学びの刻みの区切り（LAZY_EPOCH）・眠りの切り替え・保存と読み込み
- 確かめ：arkhe で「グラフあり／なし」を同じ状態から N歩回して比べる道具（GPU でしか撮れないため）
